# 重構路線圖

此路線圖採取漸進式重構，不以一次重寫為目標。核心原則是：先提高可維護性，再處理架構升級。

## 第一階段：維護基礎

目標是讓現有靜態網站具備清楚文件、安全邊界與可檢查流程。

| 工作 | 狀態 |
| --- | --- |
| 補齊 README。 | 已完成 |
| 建立 `.env.example`。 | 已完成 |
| 建立金鑰治理文件。 | 已完成 |
| 建立維護流程文件。 | 已完成 |
| 建立重構路線圖。 | 已完成 |

## 第二階段：拆分檔案

目標是降低 `index.html` 的維護壓力。

| 工作 | 建議順序 |
| --- | --- |
| 將 CSS 拆到 `assets/css/main.css`。 | 1 |
| 將 JavaScript 拆到 `assets/js/app.js`。 | 2 |
| 將機場、機體與圖層常數拆到 `assets/js/data.js`。 | 3 |
| 將 API endpoint 集中到 `assets/js/config.js`。 | 4 |
| 保留 `index.html` 作為頁面結構入口。 | 5 |

## 第三階段：API 代理

目標是避免 key 長期暴露於前端。

| 工作 | 建議順序 |
| --- | --- |
| 檢查 Google Maps API key 限制。 | 1 |
| 建立航班查詢 Worker。 | 2 |
| 建立潮汐查詢 Worker。 | 3 |
| 整併雷達與空品 Worker 文件。 | 4 |
| 前端改讀自家 Worker endpoint。 | 5 |

## 第四階段：資料管理

若儀表板未來會管理客戶、案件、報價、任務或素材，應建立後台，不建議把營運資料放在前端 HTML。

| 模組 | 說明 |
| --- | --- |
| 專案管理 | 管理空拍任務、地點、狀態與交付內容。 |
| 客戶管理 | 管理聯絡人、需求與案件歷史。 |
| 飛行紀錄 | 管理飛行日期、設備、電池、天候與風險。 |
| 素材管理 | 管理照片、影片、雲端連結與交付紀錄。 |
| 公告與設定 | 管理儀表板顯示內容、工具連結與提示文字。 |

## 第五階段：框架化評估

只有在功能持續擴張、互動狀態變複雜、或多人維護需求出現時，才建議導入 Vite、React 或 Vue。

在此之前，保持原生 HTML、CSS、JavaScript 並做好拆分，會更容易控制成本與部署風險。
